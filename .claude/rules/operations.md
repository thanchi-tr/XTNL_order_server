# 24/7 Operations, High Availability & Single-Writer Rules

This server runs 24/7 and is the backbone of the future automated trading system. These rules apply to the runtime (leader election, supervision), deployment and operational tooling. When it runs on a single PC that is not on 24/7, §17 (single-PC mode) adds the uptime record and the downtime catch-up.

1. **Topology (AWS eu-west-2):**
   - Two identical engine nodes in different AZs (2a, 2b) plus a small **non-burstable** witness in 2c.
   - etcd runs on all three (quorum 2 of 3), each member on its own gp3 volume, with `--auto-compaction-mode=periodic --auto-compaction-retention=1h`, a scheduled rolling defrag, all three endpoints configured in clients, heartbeat 250 ms / election 2500 ms. Alert at 50 % of the quota and on any etcd alarm. Patch one member at a time, and only while 3/3 are healthy.
   - Patroni manages PostgreSQL 17: a primary plus a synchronous standby, `synchronous_mode: true`, `failsafe_mode: true`, `ttl 15`, `loop_wait 5`, `retry_timeout 5`, `primary_start_timeout: 0` (with a synchronous standby, promote at once instead of retrying a primary that won't restart), `archive_mode=always` on both members. Sync replication may degrade to async only with a critical alert (`synchronous_mode_strict: false`, an accepted deviation: a lost standby stalls commits for at most ~20 s instead of until an operator acts; `deploy/patroni/patroni.yml`).
   - The engine leader prefers the Patroni primary's node, so losing one node is one failure, not two. This is a campaign **tie-break** (a preference in §4), never an abdication trigger. An alert fires when the leader has not been on the primary's node for more than 10 min; the runbook then schedules a planned engine switchover. The failure table (§6 and the Deployment page) says 'standby lost: no failover' only while they are co-located.
   - Each node has its own Redis, used only while that node is the engine leader.
   - **Optional market-data store** (design §A2; only with `XTNL_MD_ENABLED=1`): each engine node also has its own `redis-md` (`deploy/redis/redis-md.conf`, `127.0.0.1:6381`, AOF `everysec`, `maxmemory 1gb` `noeviction`, `xtnl-redis-md.service` with `MemoryMax=2G`, installed but enabled only with the flag), not replicated, separate from the engine Redis. Remote readers reach it only as `md_reader` through the node's mutual-TLS proxy (`${NODE_IP}:6382`, VPN CIDR only). Its ACL file is rendered at every start from the secrets source (`python -m src.ops.md_acl`, `#<sha256>` entries only).
2. **Single writer — lease and epoch:**
   - Exactly one engine **LEADER** holds an etcd lease (TTL 15 s, renewed every 1 s, retrying at once on another endpoint).
   - **Epoch** = (etcd `cluster_id`, lease revision); the fencing token is the revision, stored in `engine_epoch.epoch`. On winning, the bump runs **first**: `engine_epoch` is updated only if the revision is newer for the same `cluster_id`, so the epoch only ever increases. A different `cluster_id` or a 0-row bump → FENCED + critical alert; it is adopted only after operator sign-off (DR runbook). After the bump commits, the new leader terminates every backend whose `application_name` carries an older epoch (best effort).
   - **Single-leader lock-free fencing:** every engine transaction runs in READ COMMITTED and takes **no** epoch lock. Every state write is conditional on the fencing token **in the same statement**: `INSERT … SELECT … WHERE (SELECT epoch FROM engine_epoch) = $1`, `UPDATE … AND (SELECT epoch FROM engine_epoch) = $1`. A fenced write that affects 0 rows where a row was expected means the fence is lost: the transaction rolls back with `EpochMismatch` and the process hard-exits (§3); where 0 rows is also a legitimate result (`ON CONFLICT DO NOTHING`, a compare-and-set miss), one read of the epoch tells the two apart. A transaction whose last fenced statement ran before the bump committed can still commit after it; lease timing (fence 12 s < TTL 15 s, §3) and the post-bump backend termination bound that window. There are three named exceptions: the RiskSweep's read snapshot, a READ ONLY REPEATABLE READ transaction that writes nothing (every sweep write goes through a separate fenced READ COMMITTED transaction, `oversee-rules.md` §2); the idempotent spill-drain `INSERT … ON CONFLICT DO NOTHING` into `events_dlq`, which any node may run (`tier-persistence.md` §5); and the cTrader `token_generation` compare-and-set (§13).
   - **ARM exceptions** (only with `XTNL_ARM_ENABLED=1` or `XTNL_MD_ENABLED=1`; design §B3, §B5.1): (a) the ARM's read snapshots, READ ONLY REPEATABLE READ transactions that write nothing, like the RiskSweep's: the arm-tracker's account image (`PgTrackerSnapshot`) and the `S_at_T` / entry-time reads (`PgArmVersionReader`); every ARM write goes through a separate fenced READ COMMITTED transaction on the ARM pool; (b) the per-node `arm_status` heartbeat upsert and the node's market-data record in it, unfenced node telemetry like `engine_runs` (§17), keyed by node and forward-only on `md_last_write_ms`.
   - Before `COMMIT`, set `SET LOCAL statement_timeout = 0`; no `transaction_timeout`. A sync-replication cancel warning or a dropped connection at `COMMIT` is an **unknown outcome**: re-read before acting.
   - The HLC (`seq_id`) is re-seeded from `MAX(seq_id)` **after** the bump commits.
   - Only the leader opens broker sessions, refreshes tokens or sends notifications. Every one of these externally visible actions first checks `lease_deadline` synchronously.
     - **Single-PC exception** (only with `XTNL_SINGLE_PC=1`, §17; never on AWS): a node with no leader session sends its own two critical single-PC pages (`SAFE_HOLD auto-resume stopped on the single PC`, `engine not recording on the single PC`) straight to the configured Oversee channels (`DirectChannelPager`, `src/runtime/single_pc.py`; no outbox, no dedupe row, no lease check; a failed channel is tried again after 60 s and 300 s). These pages exist only while there is no leader, so no outbox can carry them; only that node produces them, and the single PC has no peer that could send them twice. With no channel configured they stay `PAGE[critical]` log lines, which `deploy/local/status-xtnl.ps1` lists. Every other page still goes through the leader's outbox.
   - `redis-md` writes carry the writer token `md:writer = (cluster_id, epoch revision, node, term nonce)`, set by a new leader after its lease check and its `engine_epoch` confirmation; every write script requires it, so a fenced ex-leader cannot write market data either (design §A7). The ARM's PostgreSQL writes are fenced like every engine write (the ARM pool runs as `xtnl_arm`).
3. **Self-fencing (off the event loop):**
   - The lease keeper runs in a dedicated thread, or in a sidecar bound to the engine unit with `BindsTo=`.
   - `lease_deadline` = the monotonic send time of the last acknowledged keepalive + the granted TTL − a margin.
   - At **12 s** without renewal it **hard-exits the engine** (SIGKILL / `os._exit`). The kernel resets the sockets: broker sockets use `SO_LINGER(on, 0)` and `TCP_USER_TIMEOUT ≤ 2 s`. systemd restarts the process into STANDBY.
   - A fence in a keeper iteration in which the machine slept more than 5 s since the previous iteration is a **sleep fence**: the process was suspended. The keeper measures the sleep with a clock pair of which one counts the machine's sleep and the other leaves it out (Windows `GetTickCount64` / `QueryUnbiasedInterruptTime`, Linux `CLOCK_BOOTTIME` / `CLOCK_MONOTONIC`), so a stalled process (a GIL hog, a VM pause, swap thrashing, a wall-clock step) is never taken for a sleep: its fence is ordinary and named `process stalled N s`. A sleep fence's reason says so (`process suspended N s`) and, just before the hard exit, the keeper appends the fence time to the node-local `sleep_fences.jsonl` next to the spill file (`src/runtime/sleeplog.py`; times only, kept 24 h). The fence itself is unchanged.
   - Ordering: **watchdog 3 s < fence 12 s < TTL 15 s**. Budget: fence − renew interval (11 s) > worst-case etcd election (2 × 2.5 s) + client endpoint failover (≤ 2 s), so losing the etcd leader's zone or the witness never fences a healthy engine. Before any planned etcd member restart, the runbook runs `etcdctl move-leader`. systemd `WatchdogSec=3`, `WatchdogSignal=SIGKILL`, fed by a 1 s heartbeat from the event loop that also asserts `lease_deadline` is in the future. The SIGKILL covers **only** event-loop lag and lease expiry. `Restart=always`, `MemoryMax`.
   - **Task supervision:** every long-running task (adapters, consumers, the Oversee feed observer, the RiskSweep, claim / trim, outbox relay, integrity worker) is restarted with backoff if it dies.
     - More than N deaths in 10 min opens a **per-task circuit**: stop restarting it, quarantine the input it was processing, page as critical, and report `degraded: <task>` in the dead-man payload. A circuit half-opens for one retry every 10 min and closes after a clean run; an audited operator `reset_task` closes it at once. Only tasks whose loss invalidates leadership (the ingestion orchestrator, the lease-keeper link) hard-exit instead.
     - If the **RiskSweep**'s circuit stays open for more than 5 min, that counts as a failed hard check, so §4 moves leadership to a healthy peer, **at most once per incident** (recorded in `cluster_state`). If the circuit then opens on the new leader too, it stays leader, keeps ingestion running and pages "RiskSweep failing on both nodes". A failure confined to one account never opens the circuit: that account is quarantined (`oversee-rules.md` §2) and the others keep being evaluated.
     - Each task stamps its liveness against its own **maximum stamp age** (for example 5 s for the RiskSweep, 30 s for the feed observer, 60 s for the outbox relay).
     - The optional market-data and ARM tasks (`optional-bootstrap`, `md-writer`, `md-bars`, `md-indicators`, `arm-status`, `arm`, `arm-relay`, `arm-config`, `arm-tracker`) are supervised, **non-critical** tasks started only after LEADER (`EngineSession.start_optional_services()`); their circuits page and feed the ARM's FAILED (design §B14) and never end the term, never hard-exit and never count as a failed hard check.
     - A task counts as alive, and is not restarted or counted as a death, while it awaits a PostgreSQL call, sleeps in SM4 BACKOFF, sits in AUTH_FAILED, or waits for SM8 READY / LEADER_INIT (it keeps stamping while it polls).
     - A stale stamp pages and restarts that task; it never kills the process.
     - Oversight cannot silently lapse: ActionGate denies every risk-increasing action unless the RiskSweep's last complete pass over the account is fresh (`oversee-rules.md` §8, the canonical gate list).
   - **Sync-standby loss:** `wal_sender_timeout` 10 s and TCP keepalives ~5 s, so commits stall at most ~20 s (until Patroni drops the sync requirement), which the stamp ages tolerate. Sockets keep draining; the bounded queues and the spooler absorb the stall.
   - Blocking SDK and DNS calls run in threads (`asyncio.to_thread`) with explicit timeouts. Event-loop lag alert at 100 ms.
4. **Node role (SM9):**
   - `STARTING → STANDBY → CANDIDATE → LEADER_INIT → LEADER → DRAINING → STANDBY`. On a fence, the process is killed and restarts at `STARTING`.
   - **Health-gated campaign:** each node publishes a health record under its own etcd lease.
     - **Hard checks:** PostgreSQL primary writable, etcd reachable, local Redis writable, chrony synced within 50 ms; for the leader only, the RiskSweep's circuit not open for more than 5 min (§3).
     - "Local Redis" is the **engine** Redis only. `redis-md` is never a hard check, never a preference and never blocks LEADER_INIT; its loss marks market-data series GAPPED (design §A2).
     - **Preferences:** a TLS handshake to each broker endpoint (ignored while that adapter's market is closed), a chrony offset < 1 ms, and hosting the Patroni primary (tie-break). For the **leader**, broker health is its own SM4 state: an adapter in STREAMING is healthy whatever a probe says.
     - The record also carries the node's spill-file size and its timestamp; a record older than 5 s counts as absent.
     - A node campaigns while it passes the hard checks, prefers to, the lease is free, it is not in back-off, and the cluster is not in SAFE_HOLD.
     - Once the lease has been free for 15 s, **any** node passing the hard checks campaigns, so a broker outage plus a leader loss never leaves the cluster leaderless.
     - **Hard-check abdication** needs the failure to persist for ≥ 2 probes over ≥ 30 s (longer than a Patroni switchover or a Redis restart, which SM8 handles in place), and a peer whose health record is newer than the start of the failure and that is an **eligible target**: it passes the hard checks, is not in back-off, and there is no SAFE_HOLD. (Eligibility ignores preferences; `may_campaign()` = eligible and the lease is free and (it prefers, or the lease has been free for 15 s).)
     - **Broker-grounds abdication** happens only when the leader's own network-level connection to a broker (DNS / TCP / TLS) has failed for `T_unhealthy` (≈20 s) while that adapter's market is OPEN, and the peer's handshake to it succeeds. Adapters in AUTH_FAILED for the current credential generation or in BROKER_MAINTENANCE count on neither side, and post-TLS errors never count. After one such abdication, no further one for that adapter until it has reached STREAMING on some node.
     - `AUTH_FAILED` is **not** a health input: it is a cluster-wide fact per adapter and credential generation (Secrets Manager version id or `token_generation`, `adapter_auth_state`), so a credential fault never causes abdication ping-pong.
   - **LEADER_INIT** order:
     1. commit the epoch bump, and in the same transaction set `stream_health.conn_lost_at = COALESCE(conn_lost_at, now())` for every (adapter, stream) (so the takeover starts fenced), insert this term into `leader_terms` and close any open predecessor term: with the `end_reason` the predecessor wrote itself (`switchover` / `abdicate`, written in DRAINING), else `init_failed` if it never reached LEADER, else `lost` (fenced or crashed). If this makes SAFE_HOLD due, set it in the same transaction and abort the term;
     2. re-seed the HLC;
     3. `FLUSHDB` the engine's own Redis database (the one `REDIS_URL` selects), never `FLUSHALL`: another database on the same server is not the engine's to wipe. `redis:boot_id` is gone afterwards, so the gate stays closed until SM8 is READY;
     4. sod catch-up: write any missing `sod_marks` row for the current trading day from `last_clean_marks`, accepting only marks with `ts` before the roll. If pre-roll inputs are missing or stale by the rule in `tier-persistence.md` §4, write the row marked `partial_session` and raise a FLAG (`MaxDailyLossRule` is then capped at SOFT); this does not exit.
     5. compute each (adapter, symbol)'s SM10 state from the versioned schedule (OPEN, ROLLOVER or CLOSED, plus any maintenance overlay); SM10's guards are level conditions (now ≥ open − 10 min, now ≥ open, …), so a takeover just before an open still runs PRE_OPEN;
     6. start SM4 for every adapter in parallel with SM8, all steps (snapshot writes queue as `NO_BOOT`; SM8 step 6 writes `redis:boot_id` after the heal and the NO_BOOT replay); the RiskSweep starts at once, reading PostgreSQL;
     7. DLQ start-up barrier.

     Any other failure is a hard exit.
   - **Deadlines** (enforced by the lease-keeper thread, independent of the event loop): LEADER_INIT must reach LEADER within 120 s, and DRAINING must finish within 10 s. On expiry the keeper revokes the lease and hard-exits (`init_failed` / `abdicate`), so a stuck node never holds the lease. On reaching LEADER, the node sets `leader_terms.reached_leader_at`.
   - Engine PostgreSQL connections use `connect_timeout` 3 s, TCP keepalives ~5 s and `statement_timeout` 5 s (except at COMMIT, §2).
   - **STANDBY** flushes the engine's Redis database on entry (`FLUSHDB`, never `FLUSHALL`), so an ex-leader's Redis never shows a frozen book.
   - **DRAINING** (planned switchover with a named target, SIGTERM, or abdication): stop intake, flush the DlqSpooler (to PostgreSQL, or to the local spill file if PostgreSQL does not answer within 2 s), write this term's `end_reason`, close sockets, release the lease. Redis is not drained, because the next leader never reads it.
     - A stop (SIGTERM) taken while CANDIDATE, or during LEADER_INIT before step 1 commits, releases the lease with no term. One taken after step 1 cancels the LEADER_INIT step in flight (never step 1 itself) and goes LEADER_INIT → DRAINING, ending the term `switchover` like a LEADER's stop: a clean stop is not abnormal, so it never counts toward the 3-in-15-min brake (it still counts as an epoch change). Fix K15, 2026-11-19, `src/runtime/node.py` `_stop_leader_init`.
     - The market-data and ARM tasks watch the stop flag and start no new write or transaction; `aclose` closes the ARM pool and the `redis-md` client in parallel with the HTTP client and the term pool inside `drain_aclose_s` (whatever has not closed is dropped). Nothing is flushed to `redis-md`; the DRAINING budget is unchanged.
   - **Hung ARM job and indicator threads:** a clean stop (after DRAINING, or a non-leader's stop) closes the ARM job runner (`JobRunner.close()`, `src/riskmgr/jobs.py`) and md-indicators' own executor (`MdIndicators.close()`, `src/marketdata/indicators/engine.py`). When either reports a thread still hung (Python cannot kill one, and the interpreter joins executor threads at exit), the process ends through `hard_exit` (`os._exit`) after the `engine_runs` stop row is written, never a normal interpreter exit, so one hung strategy or indicator cannot hold the node until systemd's stop timeout. Indicator jobs never run on the loop's default executor.
   - **Back-off:** a node waits 60 s before campaigning again after FENCED, DRAINING or abdicating, except after FENCED when no peer has a fresh (< 5 s) health record: then it campaigns as soon as it passes the hard checks. A restarted process learns this itself: at STARTING it reads `leader_terms` for its node, and an open term (`ended_at` NULL, so it was killed) or one ended `lost` / `init_failed` within the last 60 s starts the back-off. This covers fence, watchdog and crash kills alike.
   - **Anti-flap brake:** `leader_terms(epoch, node, started_at, reached_leader_at, ended_at, end_reason)`, written only by LEADER_INIT step 1, by LEADER entry (`reached_leader_at`) and by DRAINING, with `end_reason` ∈ {`switchover`, `abdicate`, `lost`, `init_failed`}. **Abnormal** = `lost`, `init_failed`.
     - SAFE_HOLD is due when 3 terms that **started** within 15 min also ended abnormally within it, or when more than 6 epoch changes of any kind happen within 30 min (a cluster-wide flap budget that also bounds abdications). Only terms ended after the last operator resume count. A term left open by a kill (a PC shutdown or sleep, a crash long ago) is closed `lost` by the next LEADER_INIT at that moment; it started outside the window, so it is no flap (fix 2026-11-18, `src/db/leader.py` `SQL_COUNT_ABNORMAL`; the ARM's `unclean_restarts` count, `SQL_UNCLEAN_ENDS`, follows the same rule).
     - **SAFE_HOLD** is a durable row in PostgreSQL `cluster_state` (mirrored to an etcd key that `may_campaign()` reads), written in the transaction that finds it due. While it is set no node campaigns, the gate stays closed, and one off-node page goes out. `resume()` (operator, audited) clears it and records the resume time.
     - **Single-PC deviation** (accepted, §17; only with `XTNL_SINGLE_PC=1`, which the AWS units never set and the engine refuses under systemd): a node that finds SAFE_HOLD set (at STARTING or in SAFE_HOLD, also a hold from an earlier run) and passes its hard checks resumes it itself after a cool-down (5 min, doubling per auto-resume within the 24 h before the hold, capped at 60 min; restarted whenever a hard check fails): the operator resume's fenced transaction, limited to the hold that was judged (same `safe_hold_since` and reason; a newer hold set meanwhile stays set and is judged afresh), with one `operator_audit` row (operator `system.single-pc-auto-resume`, no approver), then the etcd mirror and an info page (through the outbox at the next LEADER). After 6 auto-resumes within 24 h it stays held and pages critical, straight to the alert channels (§2 single-PC exception). Only auto-resumes after the last applied resume by a person count, so an operator's resume starts a fresh budget (`src/runtime/single_pc.py`, `src/db/cluster_state.py` `SQL_COUNT_AUTO_RESUMES`).
     - An off-node alert also fires on the epoch-change rate.
5. **Phase 2 send contract (written now, enforced when sending exists):**
   - Two senders are excluded only **within lease timing**; brokers never see the epoch.
   - Every send first commits an `outbound_intent` row (deterministic `client_order_id`, epoch, state `SENDING`) in an epoch-checked transaction.
   - Immediately before the socket write, with no `await` in between, check `monotonic now < lease_deadline − max_send_time`; abort if not.
   - After acquiring the lease, a new leader keeps ActionGate shut for TTL + `TCP_USER_TIMEOUT` + the broker ack timeout. It marks earlier-epoch `SENDING` intents `UNKNOWN` and resolves them only through a broker read or stream event matched on `client_order_id`, or by an operator. **Never re-send automatically.**
   - Deny risk-increasing actions until the account has been reconciled after the latest market open in the current epoch, while its adapter has an open `stream_health` row, and for an account holding a `stale_mark` symbol (canonical list: `oversee-rules.md` §8).
   - The ARM's advice is not an action: a Phase 2 sender that acts on it must treat it as actionable only per design §B10 (advice, not superseded, not PRE, not UNRESOLVED_RANGE, within its maximum age, not under FAILED), keep one non-terminal intent per stop handle with the expected broker version, and still pass `ActionGate.allow`.
6. **Recovery targets** (measure in quarterly drills, including a broker outage combined with a leader kill; publish per failure case):
   - Gate closed throughout every case below.
   - Engine crash: ~30–60 s to ingestion.
   - Node or AZ A lost: ~45–90 s (Patroni promotion + lease + LEADER_INIT).
   - PostgreSQL process failure on the primary: Patroni promotes the sync standby within ~15–25 s (`primary_start_timeout: 0`); engine commits stall meanwhile; measure in the drill.
   - Standby lost: commits stall ≤ ~20 s until Patroni drops sync, then async + critical alert; no failover while the leader is on the primary's node.
   - Witness or the etcd leader's zone lost: no outage (inside the fence budget, §3); alert.
   - Redis lost on the leader: ~10–30 s gate closed while SM8 rebuilds in place; no abdication (the Redis hard check must fail for ≥ 30 s).
   - **RPO 0** for committed data while the sync standby is healthy.
7. **Database damage:** the engine **never restores PostgreSQL** automatically.
   - Primary-only damage: HALTED + page; Patroni switchover to the sync standby after it passes the same check; `patronictl reinit` the bad member.
   - Damage on both members: MANUAL_INTERVENTION.
   - A Tier 3 restore is an operator runbook run through Patroni: pause, pgBackRest restore to an explicit target on the current timeline, reinit the replica, resume.
   - Comparisons use `recovery_target_timeline=latest`, and only up to the archived LSN.
8. **Region disaster recovery (manual only, no automatic cross-region failover):**
   - Step 1: isolate London, and revoke the London broker credentials and refresh tokens.
   - Then restore Tier 3 into a pre-provisioned stack in another region. The new etcd `cluster_id` is adopted only through the epoch sign-off rule.
   - RTO 2–4 h. RPO ≤ the WAL archive window (`archive_timeout` 60 s).
   - Any dropped WAL or timeline switch triggers an immediate incremental backup and a critical "PITR horizon broken" alert.
   - Daily incremental / differential backups; replay timed in the drill.
9. **Alerting & observability:**
   - **Off-node alerts** (CloudWatch or managed Prometheus/Alertmanager → SNS → phone), independent of the engine, the outbox and the epoch: no LEADER for more than 30 s, two LEADERs, etcd or Patroni unhealthy, sync standby missing, epoch-change rate, a non-empty spill file on any node for more than 60 s (from the health records), and **standby not ready**: a peer's health record absent or stale for more than 60 s, or a peer failing a hard check or unable to campaign (back-off, SAFE_HOLD) for more than 5 min. The quarterly drill covers 'standby not campaign-eligible'.
   - **Dashboard** (Melbourne, read-only over the VPN): entity views come from PostgreSQL; Redis live values are shown only when the Redis it reads has a `redis:boot_id` epoch equal to the epoch in the latest leader heartbeat, otherwise they are marked stale.
     - Market data read from a node's `redis-md` is shown only while that node's `md:writer` epoch equals the epoch in the latest leader heartbeat (otherwise `STALE_NODE`), and only as a display "best bar" labelled with its source (BROKER or TICK).
   - **Live view** (single PC only, `src/liveview/`, `docs/runbooks/live-view.md`): a local read-only page on `127.0.0.1:8090` (literal loopback only) that reads only the `lv_` views of migration 0021 through the `xtnl_liveview` login, plus the allow-listed lines of the engine's loopback metrics endpoint; it never sends orders, has no write path and no Redis connection, shows ids, times, codes, counts and order levels only, and is no alert path (pages still go through the outbox and the channels).
   - **Push dead-man's switch:** every 15 s the leader POSTs {node, epoch, gate state, halt level, per-adapter SM4 state, age of the last committed broker event, oldest un-acked feed entry, the oldest per-account RiskSweep pass age, per-adapter `market_open` (SM10) and `maintenance_until`, the calendar version, oldest undelivered `notification_outbox` row, SM8 / SM5 state, spill-file size, `degraded` task list}.
     - Melbourne pages through a channel **outside eu-west-2** (SNS in ap-southeast-4 or a third-party pager).
     - It pages after 60 s of silence, when **any** adapter has not been STREAMING for 2 min while its `market_open` is true and it is not in maintenance, when those fields are missing, or when an age passes its threshold (feed entry > 30 s, any account's RiskSweep pass > 10 s old, alert undelivered > 60 s, SM8 not READY or SM5 UNKNOWN > 60 s, spill file non-empty > 60 s), or when any task circuit is open.
     - A daily test page proves the path.
     - **Receiver not acknowledging** (home-server W1, `src/runtime/deadman.py`, `docs/runbooks/deadman-alert.md`): when the leader's main beats have failed for `XTNL_DEADMAN_ALERT_AFTER_S` (60–3600 s, default 300), it sends one PAGE[high] "dead-man receiver not acknowledging" through the outbox, once per episode, and PAGE[info] when beats are acknowledged again; the episode is kept in `notification_dedupe`, so a new term within 6 h of the episode's page neither re-pages it nor loses its recovery page; an inherited episode paged more than 6 h earlier (`INHERITED_EPISODE_MAX_AGE_MS`) is paged again by a term whose own beats fail for `XTNL_DEADMAN_ALERT_AFTER_S`. A set `XTNL_DEADMAN_URL` without `XTNL_DEADMAN_TOKEN` logs an ERROR at start. The leader exports `xtnl_deadman_configured`, `xtnl_deadman_consecutive_failures` and `xtnl_deadman_last_ok_age_seconds` (absent until the term's first acknowledged beat).
     - **Two engines beating** (home-server W19, `src/deadman_receiver/evaluate.py`): the receiver tracks beats per (node, epoch) and pages critical when two sources beat interleaved inside its window (held, so it never flaps), and sends a notice when the beating node changes (one such notice is expected after the operator renames `XTNL_NODE_ID` on the same box; it clears after 5 min).
     - With the ARM on, the payload also carries `arm_failed` (open FAILED scopes, global flag) and `arm_overdue_positions` (optional fields; the receiver accepts their absence). `arm_overdue_positions` counts the armed positions (ARMED, TRACKING, ADVICE_OUTSTANDING; not FAILED, no pause) with more than 2 OPEN bars past their decision cap undecided, or whose symbol has no loaded schedule (`src/riskmgr/liveness.py`); the receiver pages above 0. Locally the `arm-status` loop pages the same condition, a BarClock with no completed pass for 60 s, an arm-tracker with none for 120 s and an unsent ARM notice older than 15 min, each once per episode. The ARM's FAILED ping (design §B14, PR4) is committed with its critical outbox copy in one fenced transaction and also exported as `xtnl_arm_failed_scopes` (off-node `XtnlArmFailed`), so a FAILED ARM pages even when its own channels are down. On a single PC without an off-PC receiver the ping goes out when PostgreSQL returns (accepted).
     - **Notification content** (Oversee and ARM): ids, codes, counts, levels of orders (entry, stops) and times only; never a tick, bar, quote, spread, indicator value or a value a close can be recomputed from (favour R, favour / risk). Exception (owner decision 2026-11-21): the email's HTML part may show an order level's distance from the entry in pips (`src/notifications/email_theme.py`, computed at send time from the instrument's `point_size`); the pip / point size itself is never shown, stored in a notice or logged. The ARM notice body in the outbox holds ids and outcome codes only; favour R is rendered at send time from a hash-checked market-data read and omitted when unavailable.
   - **Inhibition:** an epoch change suppresses dependent alerts (stale / FENCE, lag, sync-degraded) for RTO + 30 s, then sends one summary or one escalation. Declared maintenance windows suppress sync-degraded.
   - Off-node rules, alarms and the metric contract live in `deploy/observability/` (generated from one table by `gen_alerts.py`; `metrics.md` is what the engine exports). Accepted deviation: CloudWatch cannot group, so each epoch-dependent alarm is held back by its own composite alarm (`ActionsSuppressor`) instead of one summary; Alertmanager sends the grouped summary.

   - **Metrics:** ingest rate per stream, queue / spool ring / DLQ depth, feed lag and PEL size, RiskSweep pass duration and age, event-loop lag, clock offset, replication and WAL-archive lag, Redis memory, disk %, REST budget use, lease-renew p99 (alert > 500 ms), role and epoch per node, token age, certificate expiry.

10. **Market calendar (SM10):**
    - SM10 is keyed by **(adapter_id, symbol)** and initialised from the schedule at LEADER_INIT (§4 step 5), because schedules, holidays and maintenance differ per broker. BROKER_MAINTENANCE is per adapter. An adapter's market is OPEN when any of its subscribed **held** symbols (orders, positions, configured `tick_symbols` and their crosses) is OPEN for it; a tick-only symbol (PR5) never decides it.
    - Sessions and holidays are loaded per (adapter, symbol) from the brokers (cTrader symbol schedule and holidays; StoneX market information or a reviewed config) and versioned in PostgreSQL.
      - **Review** (`src/runtime/schedule_refresh.py`): a missing symbol, a documented default, unknown holidays or a broker note pages "market sessions need review" (info). A symbol whose stored `reviewed_config` row the merge keeps (the broker gave nothing or only a flagged default) is left out of the default / holidays / note entries; a missing symbol is still reported. The last paged set is kept per adapter in `notification_dedupe` (rule `market_sessions_review`), so an unchanged set pages once per change, not once per term; a different set, or the same set after a clear, pages again (fix 2026-11-25, live review: StoneX FX paged on every start).
      - **Accept** (audited operator CLI, `src/ops/market_sessions.py`): `python -m src.ops market-sessions accept --adapter A --symbols S1,S2 [--holidays FILE.json]` copies the stored schedule of each named symbol into a `reviewed_config` row (`is_default=false`, empty note, `holidays_known=true` only with a holiday list), checked with the engine's parser, and writes a new `calendar_version` under the engine writer's advisory lock, fenced on the stored epoch, with its `operator_audit` row in the same transaction; an unchanged set is a `noop`. `market-sessions show` is the read-only view. The leader loads the version at its next schedule save (6 h or the roll) or its next start. Operator step for StoneX EURUSD / AUDUSD: once their FX hours are checked against StoneX, run `accept` for them.
    - **While CLOSED or in ROLLOVER**, only **price** staleness is suppressed. Order / account liveness and auth failures still alert.
    - **BROKER_MAINTENANCE** is an expected adapter outage and a per-adapter **overlay** entered from any session state (a window often falls while the market is closed): normal backoff, one pre-acknowledged notice, and liveness / FENCE alerts suppressed for that adapter. When the window ends, each symbol returns to its scheduled state, running the PRE_OPEN readiness check first if an open passed during the window; FENCE is at full severity from then on.
    - **Evidence beats the calendar:** while CLOSED, only **symbol-specific** evidence switches a symbol to OPEN (with `FLAG calendar_mismatch`): a tick on that symbol with a broker timestamp after the scheduled close and a price that differs from the last pre-close quote, or an execution event on that symbol. Subscription snapshot items and account or cash-flow events don't count. The symbol then sits in **OPEN_BY_EVIDENCE**, which returns to CLOSED after 30 min without such evidence; the scheduled PRE_OPEN runs from there too. A scheduled-OPEN symbol with no ticks is never moved to CLOSED: the stale-price page fires instead.
    - **PRE_OPEN readiness check** (open − 10 min and after each roll): reset backoff and reconnect, take a fresh account snapshot and `fetch_cash_flows`, confirm tokens are valid > 24 h and chrony is synced, and page if any adapter is not STREAMING.
    - **At the open:** STREAMING adapters run REST-only RESYNCING with jitter at open + 30–60 s; the others go through SNAPSHOTTING.
11. **Data lifecycle:**
    - Partition `event_log`, `account_snapshots` and DLQ history by **`seq_id` range** (the HLC maps fixed ranges to roughly monthly windows), so unique keys survive. DLQ history is `events_dlq_history`: the lifecycle task moves `RESOLVED` `events_dlq` rows there 7 days after resolution, with `seq_id = resolved_at_ms << 20 | (dlq_id & 0xFFFFF)` (accepted deviation: `events_dlq` rows carry no HLC `seq_id`, so the resolution time stands in for it). `oversee_events` is partitioned by `sweep_id` range (an HLC, so by time) and `notification_outbox` by `created_at` (`tier-persistence.md` §4).
    - Outbox rows are deleted after relay. 90 days hot in PostgreSQL.
    - Older partitions are exported and **verified** (row count + checksum) before detach or drop. The leader's lifecycle task writes each partition past the hot window as gzip JSONL (one `to_jsonb` row per line, from one read-only snapshot) with a `.sha256` sidecar to `XTNL_ARCHIVE_DIR`, reads it back (gzip CRC, line count, sha256), and only then records the fenced `partition_archive` row; the detach requires that row and an unchanged row count. The directory is copied to S3 by the operator job in the runbook (`partition-archive.md`). Gzip JSONL instead of Parquet is an accepted deviation (standard library only, no schema mapping). Dropping a detached table stays an operator action. Audit tables (`halt_events`, `oversee_events`, `cash_flows`, `leader_terms`) are kept per compliance and never exported or detached by the engine.
      - `arm_decisions` and `arm_decision_handles` (partitioned by `bar_end_ms`, months created ahead by the lifecycle task, a DEFAULT partition that stays empty and pages if not) are audit tables too: kept hot, never exported, detached or dropped by the engine.
      - `redis-md` retention is enforced by md-writer (`RETAIN` for ticks and TICK bars, `RETAIN_BROKER` for every stored BROKER series, 1 year, design §A5), never by PostgreSQL lifecycle; no market data is ever archived.
    - Autovacuum tuned; disk alerts at 70 / 85 %.
    - `last_clean_marks(adapter_id, symbol, bid, ask, ts)` is upserted at most every 10 s per (adapter, symbol) and forced at each open / closed / roll transition, epoch-checked.
12. **Change management:**
    - Rolling upgrade by switchover: upgrade the standby, switch to it, upgrade the old leader.
    - Schema migrations are expand / contract, compatible across N and N+1, run as an operator job **before** the switchover (never at engine start-up), with `SET lock_timeout = '2s'` and retries (a lost lock wait or deadlock is rolled back and retried 5 times with back-off). An applied file never changes, except a reviewed comment-only edit listed in `src/db/migrate.py` `ACCEPTED_REVISIONS` with its comment-free checksum (accepted deviation, used for 0008's stale exporter comments). Every runner applies migrations only up to the local setting `XTNL_MIGRATIONS_ACCEPTED_UPTO` (default 14, `src/db/migrate.py`); later ones are held back, named in one line, and the job exits 0, so a start that runs it (the single-PC `start-xtnl.ps1` step 6, §17) never puts an unreviewed migration live. On a schema without the 0015 columns every pool runs the core statements in their 0014 form and the orchestrator publishes rows in their pre-0015 shape (`src/db/schema_compat.py`), so the engine behaves as before (accepted deviation: the single PC runs the operator job at its own start, gated by this setting).
      - On a partitioned table (`event_log`, `notification_outbox`, `arm_decisions`) a new column is nullable with no default; a new CHECK is added `NOT VALID` and validated by the no-transaction post step of `src/db/migrate.py`; a new index is created `ON ONLY` the parent and built per partition `CONCURRENTLY` by the post step, then attached (migrations 0015-0017, design §C1).
      - The `lv_` views of migration 0021 (the live view) pin their base columns: a migration that changes the type of a column such a view reads, or drops one, must drop and recreate the affected `lv_` views in the same migration, with their `xtnl_liveview` grants (`src/liveview/sql.py` `ALL_VIEWS` and the grants stay equal).
    - Major PostgreSQL upgrades need a `pg_upgrade` window or a logical-replication blue/green cut-over with the gate closed.
    - Rule thresholds are versioned in PostgreSQL (`ruleset_version`). A reload calls `sweep_now()` for every account and is audited (`oversee-rules.md` §7).
    - `rulesets` rows are written only through the audited operator CLI: `ruleset add` validates the document with the engine's own parser (`parse_ruleset`) and stores it inactive as the complete `ruleset_json`; `ruleset activate` (two people) re-validates the stored row and makes it the single active one. `rulesets` is operator-owned config the engine only reads, so these writes run under a table lock instead of the epoch fence.
    - `arm_accepted` and `arm_controls` (the ARM's accepted configuration hash and its pause / drain controls) are operator-owned configuration the engine only reads, written only by the audited operator CLI (`arm config accept`, `arm pause` / `resume`, `arm notify-test`) under a table lock with the `operator_audit` row in the same transaction, like `rulesets`.
13. **Credentials & secrets:**
    - AWS Secrets Manager, refreshed periodically; rotation without restart. This holds for the Melbourne services too (fix 2026-11-18, K10): the dead-man receiver re-reads its bearer tokens every tick and its paging channel credentials every minute from its own secret; the dashboard re-reads its PostgreSQL DSN and Redis URLs every minute (`src/dashboard/rotation.py`: a new read-only pool / new clients swapped in place) and its heartbeat listener file every 30 s (`token`, optional `token_next`, a replaced token accepted for `token_overlap_s`), so the engine's `XTNL_HEARTBEAT_COPY_TOKEN` (re-read from the engine secret, at once after a 401) rotates without a refused copy; a source that becomes unreadable or invalid keeps the last valid credentials. Server certificates are re-loaded in place when their files change. Accepted deviation: the receiver unit takes its TLS files through `LoadCredential=` (copied at start), so a renewed receiver certificate takes a 5 s restart; listen addresses, paths and channel kinds also take a restart.
    - The cTrader token pair is **state**: refreshed only by the leader in a lease-checked step days before expiry, and **saved before use** in one store, a KMS-encrypted PostgreSQL row with `token_generation`. The leader refreshes only with at least **8 s** of lease left (`lease_valid(8)`) and only after committing a 'refresh in flight' row for generation N. The bound must be reachable: with TTL 15 s, renewal every 1 s and the fence at 12 s, a healthy lease never has more than ~11 s left (fence 12 s − renew 1 s), so the earlier 30 s could never be met; 8 s still leaves the refresh round trip inside the lease; the new pair is saved with a compare-and-set on `token_generation` that is **not** epoch-gated (like the spill drain), so a save started before a leader change still lands, and a later leader never refreshes generation N twice. Keep it in memory and retry the save until it succeeds. LEADER_INIT reads it fresh. The standby never refreshes.

    - Credential errors (bad password, PasswordChangeRequired, `invalid_grant`, TokenInvalidated after a fresh read) go to SM4 `AUTH_FAILED`: at most 3 attempts, then a critical page, no backoff loop.
    - The token row carries a monotonic `token_generation`, bumped on every save, used with the Secrets Manager version id as the credential generation in `adapter_auth_state`. SM4 leaves `AUTH_FAILED` for AUTHENTICATING when the generation changes or an operator re-arms the adapter.

On the single PC (§17) the API certificate is exported as `api-server`; there is no off-node path there (accepted, as for every other off-node alert).

15. **Rate limits:** one REST token bucket per adapter is shared by snapshots, resync re-reads, DLQ checks, cash-flow fetches, the 60 s account poll and (only with the optional market-data / ARM services on) broker bar reads and the ARM's stop reads, with priority reconcile > on-demand cash-flow fetches requested by Oversee or an operator (relayed by the orchestrator, at most once a minute per account) > bars > DLQ > poll. The ARM's entry-time history read (`IngestionOrchestrator.history_execution_time`, plan S39b: one `fetch_history` per armed position whose entry time is still ESTIMATED, at most once a minute and 5 times per term, only until bar 0's decision cap) runs in the reconcile class; it publishes and writes nothing.

REST failing at every priority with a recent outcome (last 60 s) is a broker outage (`broker_unavailable`, never an ARM FAILED); failures only at `bars` are bar-read failures; with no recent non-`bars` outcome the verdict is unknown and decides nothing.

17. **Single-PC mode (the engine is not on 24/7):** the server also runs on one Windows PC that sleeps, shuts down and restarts (`deploy/local/run-local.ps1`; runbook `docs/runbooks/downtime-catchup.md`). Everything above still applies; this adds what keeps the internal state equal to the broker's across the time the engine was off.
    - **Uptime record** (`src/runtime/uptime.py`, migration 0012, every node and role): an `engine_runs` row at start (`run_id`, node, `started_at_ms`), a light heartbeat every `XTNL_UPTIME_PING_S` (60–1800 s, default 900) updating `last_seen_ms`, and at a clean stop `stopped_at_ms` + `end_reason` (`SIGINT`, `SIGTERM`, `stopped`, `fenced`, `error:<type>`). A hard exit or power loss leaves the row open; its `last_seen_ms` is the last proof of life. While this node is the LEADER the heartbeat also advances `adapter_coverage.last_streaming_ms` for every adapter that is STREAMING, reconciled and whose catch-up **vouches** for it (finished, not retryable-incomplete, no interruption since its read). These are node telemetry, written without the epoch fence (the coverage upsert is skipped, never raised, when the writer's epoch is no longer current, and only moves forward).
    - **Sleep detection:** a 5 s tick compares wall-clock and monotonic deltas; a wall jump the monotonic clock did not follow (or both far beyond the tick), larger than max(2 × tick, 120 s), counts as a suspension: `suspended_gaps` +1, an immediate heartbeat, and on the leader a forced SM4 RESYNCING plus a `resume_after_sleep` catch-up for every adapter. If the sleep outlived the lease, the fence hard-exits the process instead (§3) and the restart runs a `startup` catch-up; `run-local.ps1` restarts the engine after a hard exit (exit codes 70–79). With the ARM on, the suspend signal also reaches every strategy job (`JobRunner.note_suspended`: a job whose run spans the sleep gets a fresh awake cap and is never counted as a timeout or a strategy fault) and the market-data layer's receipt-gap watch, which the orchestrator feeds with every prices-stream heartbeat (`on_stream_frame`, plan S39b). On Windows the monotonic clock keeps counting through a sleep, so a sleep longer than the fence is the usual case: the keeper fences on wake (a sleep fence, §3) and `run-local.ps1` restarts the engine. The `md-writer` and the BarClock also detect a suspend themselves (both clocks moved more than 10 s between two 250 ms passes) and take the uptime tracker's signal (`EngineSession.add_suspend_listener`): the TICK buckets the sleep covered are `blind` and the BarClock holds one pass. The ARM does not count a sleep fence's own restart toward `unclean_restarts` (the first `lost` / `init_failed` term end within 15 min after a recorded sleep fence) and pages each sleep restart once ("ARM: engine restarted after a PC sleep").
    - **Downtime catch-up** (`src/runtime/catchup.py`, leader only, per adapter, reasons `startup`, `resume_after_sleep`, `operator`, `reconnect`, `retry`):
      1. the adapter's `stream_health` fence is held from before SM4 starts (or from the resume) until the catch-up has finished and paged;
      2. after the first committed SNAPSHOTTING / RESYNCING pass (STREAMING), the window is `adapter_coverage.last_streaming_ms − XTNL_CATCHUP_OVERLAP_S` (≥ max(ping, 300 s), default 900 s) to now. Coverage ahead of the wall clock (the clock was stepped back) never gives an empty window: it proves nothing about when the engine stopped, so the start is that of a window without a coverage row (below; never later than now − overlap), the catch-up is incomplete and `clock moved back` is paged (PAGE[high], once per term per adapter). Without a coverage row the window starts at the oldest of now − `XTNL_CATCHUP_FIRST_RUN_DAYS` (1–365, default 7), the oldest stored working order / OPEN position, and the engine's last known active time before this term (the earliest last-seen / stop time of any earlier `engine_runs` row, and the newest `event_log` row written before the term); a start older than 365 days is cut there, recorded incomplete and paged with the part not read;
      3. `fetch_history(since, until)` (`adapter-isolation.md` §4) and `fetch_cash_flows(since)` are read and every row goes through the orchestrator's normal REST path (version compare, event_log, outbox, Redis apply in the consumers); an untimed history row in a broker-time domain is skipped and reported, never labelled with the watermark (the incomplete page and the `catchup_runs` notes name its entity id, at most 10 then a count, and the whole read window as uncovered, since no time narrows it); a CLOSED history position without an entry price keeps the side and entry this term already knows, and every row keeps the known facts of its entity (`dto-contracts.md` §2: entry price, parent link; the stored rows the catch-up touches are loaded first, so this holds after a restart too). The history may carry several versions of one order (StoneX: a stop / limit order WORKING at its placement, then CANCELLED / FILLED); each is submitted oldest first per entity and lands in event_log as its own APPLIED version, a version older than the stored row is a normal stale drop (never an anomaly), re-reading a window only advances stored versions (same checksum: no new APPLIED row), and the `catchup_runs` counts are per entity, not per version. Rows committed by an earlier catch-up keep their single stored version: a later read applies the new links and flags on the terminal version, but its placement version is older and drops as stale. A row the adapter cannot map during these reads (or the by-id re-reads of step 4) counts on the read's own channel (`history_read`), makes the catch-up incomplete and never counts on the live-stream `unmapped_rows`: it is never taken for, and never hides, a live-stream interruption;
      4. every stored working order / OPEN position in neither the latest snapshot nor the history is re-read by id; "not found" is an anomaly, never a close;
      5. one fenced `catchup_runs` row (counts of what the catch-up itself added on top of the snapshot: orders new / updated, positions new / closed, cash flows new, anomalies; `complete`; notes without amounts), a PAGE[info] summary after a downtime, and PAGE[high] "downtime catch-up incomplete" naming the uncovered window while the fence is still held;
      `complete` is about orders and positions only: a partial cash-flow ledger (a StoneX closing trade without RealisedPnl; the 2026-11-14 live cases were opening trades listing only their own id in `OpeningOrderIds`, now read as openings, `adapter-isolation.md` §2) is noted on the row and pages separately as "cash-flow ledger incomplete" (P&L stays unverified, `oversee-rules.md` §5) but never makes the order catch-up incomplete. StoneX answers a closed position's `order/{id}/openposition` with HTTP 403 / ErrorCode 80001; the by-id re-read reads that as "no longer open" (not as an explicit not-found) and the close comes from the trade history.
      6. the hold is released. An incomplete catch-up caused on this side or by a passing failure (failed reads or re-reads; a history answer whose `BrokerHistory.retryable` is not False: a failed or timed-out page or request, a throttle or maintenance code, a refused request budget, a row the adapter could not map, evidence that did not add up between reads; rows not committed or parked on a full topic) holds coverage back and retries after 5 min, doubling to 1 h. An incomplete answer whose cause is unknown counts as retryable (fail closed). Only a genuine limit is paged once while coverage moves on: retention, the broker's own truncation / paging limit or incomplete flag, the unconfirmed StoneX paging rule or stop / limit history switch, no history facility, a "not found" by id, a row without a version, the 365-day cut and a clock stepped back. Either way ActionGate denies the adapter's risk-increasing actions for the rest of the term until a catch-up is complete (`oversee-rules.md` §8, `catchup_unverified`).
    - **Mid-run interruptions:** a gap, socket loss, auth loss or a live row the adapter could not map on the orders / account path stops coverage at once (orders placed and finished during it are in no snapshot), also while a catch-up is running: the catch-up never reverts `last_interruption_seq`. A `reconnect` catch-up re-reads the history once a pass sent after the interruption has committed.
    - **Read-only:** every catch-up call is a broker read on the read-only allow-lists; nothing sends, modifies or cancels an order. Logs, pages and tables carry counts, ids and times only, never an amount.
    - **Self-healing start** (accepted deviation, `XTNL_SINGLE_PC=1`, set by `start-xtnl.ps1` / `run-local.ps1`): SAFE_HOLD auto-resumes after a cool-down (§4); a node without a leader term for 10 min pages critical ("engine not recording", once per episode, info when it records again). Pages of a non-leader are logged; its two critical single-PC pages also go straight to the configured alert channels (§2 single-PC exception), and the info pages (auto-resumed, recording again) go to the outbox at the next LEADER. `start-xtnl.ps1` starts the engine even when its 15-min clock wait gives up (the engine's own clock hard check keeps it from leading until the clock passes), logs an `ALERT:` line after 30 min of failed attempts (hourly after) and on a configuration stop (78); `run-local.ps1` logs one for 5 hard exits within 30 min. Before the engine runs, the log is the only channel on this PC; `status-xtnl.ps1` lists the last `ALERT:`, `PAGE[critical]` and `direct page` lines of every log.

Its environment lacks every `$LiveViewDropEnv` name (explicit prefixes and names only, never a wildcard that would match `XTNL_LIVEVIEW_DSN`); `XTNL_LIVEVIEW_DSN` is refused in the env file and dropped from the engine and API children.
    - **Home-server secrets** (W2, `docs/runbooks/single-pc-autostart.md`): `XTNL_HEARTBEAT_COPY_URL` and `XTNL_HEARTBEAT_COPY_TOKEN` come only from the Windows User environment (refused in the env file, exit 78; passed to the engine only, dropped from the API and live view). That warning means the secrets leaked: the operator rotates them at once, and check C runs recorded from the earliest time they may have leaked until the rotation are never trusted for a restore; runs from before that time stay trusted (home-backup-restore.md "If a backup secret leaked", review rounds 5 and 7). Only `XTNL_BACKUP_HC_URL` and the B2 upload key are secret: names that are all non-secret (`XTNL_BACKUP_B2_BUCKET`, `XTNL_BACKUP_AGE_RECIPIENT`, `XTNL_BACKUP_EXCLUDE_MARKS`, `XTNL_BACKUP_ARCHIVE_HOST`) log a separate `non-secret backup names` warning: delete them, nothing is rotated or distrusted. Restore reads a hidden or replaced pre-leak backup at its locked older version (`rclone --b2-version-at`, review round 7). A theft of the PC is such a leak too: its window starts at the last time the PC was known to be in the operator's hands, and every check C run and `daily/` folder from then until the rotation is rejected for a restore (review round 6). A backup secret pasted into a window on the `xtnl` desktop (a runas window included) is a leak too: rotate it at once with a rotation note whose window starts at the paste (review round 8).
