# Off-node alerts (Alertmanager / CloudWatch -> SNS)

Phase 1 never sends orders. These alerts are evaluated off-node (operations.md §9), independent of the
engine, its outbox and the epoch: Prometheus rules `deploy/observability/prometheus/xtnl-alerts.rules.yml`
with `deploy/observability/alertmanager/alertmanager.yml`, or the equivalent CloudWatch alarms
`deploy/observability/cloudwatch/xtnl-alarms.json`. Both are generated by
`deploy/observability/gen_alerts.py` from one table; the metrics are defined in
`deploy/observability/metrics.md`. Engine-side pages (halts, FENCE, stale prices, the Melbourne dead-man)
are separate: see deadman-alert.md, halt-clear.md.

## Trigger

An SNS page or e-mail whose subject starts with `[XTNL CRITICAL]` / `[XTNL warning]`, or a CloudWatch alarm
named `xtnl-*`. The body names the rule (`XtnlNoLeader`, ...) and links to the section below.

## Checks

```
curl -s http://$NODE_A_IP:9464/metrics | grep -E '^xtnl_(node_role|engine_epoch|health_)'   # what node A exports
curl -s http://$NODE_B_IP:9464/metrics | grep -E '^xtnl_(node_role|engine_epoch|health_)'
$ETCDCTL endpoint status -w table
patronictl -c /etc/patroni/patroni.yml list
$OPS safe-hold status
$OPS epoch show
journalctl -u xtnl-engine --since "-15 min" | grep -E "role|fence|abdicat|SAFE_HOLD"
```

Inhibition: for RTO + 30 s (120 s) after an epoch change (`XtnlEpochChangeSettling`), the dependent
alerts (sync standby missing, replication lag, feed lag; label `depends_on_epoch="true"`) are held back, then
sent as one grouped summary per severity if still firing (a dependent warning stays on the warning topic).
A **declared maintenance window** (planned PostgreSQL / node work; broker maintenance windows are declared
separately, `broker-maintenance.md`) suppresses sync-degraded:
silence it before the window starts (CloudWatch: disable the `xtnl-sync-standby-missing-notify` actions):
```
amtool silence add alertname=XtnlSyncStandbyMissing --start=<ISO start> --end=<ISO end> --comment="<ticket>"
aws cloudwatch disable-alarm-actions --alarm-names xtnl-sync-standby-missing-notify   # re-enable after the window
```

## Commands

### XtnlNoLeader
No node is LEADER for 30 s. Check SAFE_HOLD (`$OPS safe-hold status`; safe-hold.md), back-off and hard
checks in both nodes' journals, and etcd / PostgreSQL health. A node in back-off campaigns after 60 s.
Failover cases: failover-and-switchover.md.

### XtnlTwoLeaders
Two nodes report LEADER for 15 s: a fencing failure. The node with the older `xtnl_engine_epoch` must fence
itself (12 s); if it does not, stop it: `sudo systemctl kill -s SIGKILL xtnl-engine` on that node, then open
an incident. Never stop both.

### XtnlEngineDown
A node exports nothing for 60 s (process down, node lost, network). `systemctl status xtnl-engine` on the
node; install-node.md for a crash loop. While one node is down the cluster has no takeover target.

### XtnlHealthRecordStale
A node's etcd health record is absent or older than 5 s for 60 s (standby not ready). Check the node's
engine and its etcd lease: `$ETCDCTL get --prefix /xtnl/health/`.

### XtnlStandbyNotEligible
A node fails a hard check or cannot campaign (back-off, SAFE_HOLD) for 5 min. Its journal names the failing
hard check (PostgreSQL primary writable, etcd, local Redis, chrony). The quarterly drill covers this case.

### XtnlSpillFileNonEmpty
A node's DLQ spill file has not drained for 60 s: dlq-quarantine.md ("Spill file non-empty").

### XtnlSafeHold
SAFE_HOLD is set (anti-flap brake): safe-hold.md. One page only; it clears with the audited resume.

### XtnlEpochChangeRate
3 or more epoch changes in 30 min (SAFE_HOLD at more than 6): find the cause in `$OPS epoch show` (terms and
end reasons) before the brake engages.

### XtnlEpochChangeSettling
Never notifies: it is the inhibition source (RTO + 30 s after an epoch change).

### XtnlLeaderNotOnPrimary
The engine leader has not been on the Patroni primary's node for 10 min: schedule a planned engine
switchover to the primary's node (failover-and-switchover.md).

### XtnlLeaseRenewSlow
etcd lease keepalive p99 above 500 ms: check etcd latency (`$ETCDCTL endpoint status`, disk fsync on the
members) before it reaches the 12 s fence.

### XtnlEtcdUnhealthy
An etcd member does not answer from either node. Quorum is 2 of 3: one member down is no outage, two is.
Restart the member (`systemctl restart etcd` on it, one member at a time, only while the others are healthy).

### XtnlEtcdNoLeader
etcd has no raft leader: no lease can be renewed and the leader fences at 12 s. Restore quorum first.

### XtnlEtcdAlarm
`$ETCDCTL alarm list`. NOSPACE: compact and defragment one member at a time, then `$ETCDCTL alarm disarm`.
CORRUPT: replace the member from a healthy snapshot.

### XtnlEtcdQuota50
Database above 50 % of quota (2 GiB): check compaction (`--auto-compaction-retention=1h`) and run the rolling
defrag (`$ETCDCTL defrag --endpoints=<one member>`).

### XtnlPatroniUnhealthy
A Patroni member is not running / streaming: `patronictl list`; failover-and-switchover.md (standby lost).

### XtnlPatroniNoLeader
No PostgreSQL primary: Patroni promotes the sync standby within ~15-25 s; if not, failover-and-switchover.md.

### XtnlSyncStandbyMissing
Sync replication degraded to async (RPO 0 lost): restore the standby (`patronictl reinit <member>` if it is
damaged). Suppressed during a declared maintenance window (above).

### XtnlReplicationLag
A standby replays more than 10 s behind: check its disk and network; it must catch up before any switchover.

### XtnlPitrHorizonBroken
WAL archiving failed or the timeline switched. `xtnl-pitr-guard` has already started an incremental backup on
the primary (journal tag `xtnl-pitr-guard`). A backup that fails is retried by the next timer run (every
minute) until it succeeds, because the guard records the new baseline only after a good backup; confirm it
finished, then fix archiving:
```
journalctl -t xtnl-pitr-guard --since "-1 h"
sudo -u postgres pgbackrest --stanza=xtnl check
sudo -u postgres pgbackrest --stanza=xtnl info
sudo -u postgres /usr/local/bin/xtnl-pitr-guard backup "<ticket>: manual after archive fix"
```

### XtnlDisk70
Disk above 70 %: partition-archive.md (export / detach), WAL archive queue, journal size.

### XtnlDisk85
Disk above 85 %: act now; same as XtnlDisk70, and check `archive-push-queue-max` in pgbackrest.conf.

### XtnlWitnessDisk70
The witness's disk (`/` or the etcd volume `/var/lib/etcd`) above 70 %: etcd data and journal on the witness.
The alarm also fires when the witness's CloudWatch agent stops reporting (missing data counts as breaching):
on the witness, `sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status` and
`df -h / /var/lib/etcd`; reload the agent with `cloudwatch/agent-witness.json` (install-node.md, witness).

### XtnlWitnessDisk85
The witness's disk above 85 %: act now (an etcd member without space raises NOSPACE).

### XtnlCertExpiry
A certificate expires within 30 days: renew it from the internal CA and reload the service that uses it
(etcd, Patroni REST, PostgreSQL, the Redis TLS proxy), one node at a time. `cert` names it: the files of
`XTNL_METRICS_CERTS` on that node, or an endpoint of `XTNL_METRICS_CERT_ENDPOINTS` read from that node
(`etcd-witness-server` / `etcd-witness-peer`: the witness's etcd member; `deadman-receiver` /
`dashboard-heartbeat`: the Melbourne listeners, which load a renewed certificate without a restart within 60 s).
The Melbourne-local client certificate (the dashboard's Redis client certificate) is watched by the dead-man
receiver itself (`XTNL_RECEIVER_CERTS`, a `cert:<name>` page from Melbourne).

### XtnlCertUnreadable
A configured certificate could not be read for 15 min (missing file, no read permission for the `xtnl` user:
certificates are public, install them 0644 in a traversable directory, install-node.md step 3b), an endpoint's
certificate did not verify (expired, untrusted, wrong name; the handshake trusts the entry's `ca=`, else
`XTNL_ETCD_CA` for the `etcd-*` names, else `SSL_CERT_FILE`; the engine logs `cert endpoint <name>: no trust
source ...` at start when only the system store is left), or the node exports fewer than the required
certificates (one left out of `XTNL_METRICS_CERTS` / `XTNL_METRICS_CERT_ENDPOINTS`, engine.env.example; each
name must point at the file its service loads, not a copy). Fix the file or the setting; the series returns
within 30 s (files) or 300 s (endpoints). CloudWatch: while the node's `xtnl-engine-down-<node>` alarm is in
ALARM (planned stop, node lost) the per-certificate alarms are held back (composite `-notify` alarms with that
ActionsSuppressor), so a down node pages once, as XtnlEngineDown.

### XtnlEventLoopLag
Engine event loop lagging more than 100 ms for 30 s (the watchdog kills at 3 s): the journal names slow
calls; check CPU steal and memory on the node.

### XtnlRedisMemoryHigh
Redis above 80 % of maxmemory (`noeviction`): check `XLEN oversee:feed` and the trim task; redis-loss.md if
it restarts.

### XtnlFeedLengthHigh
`oversee:feed` above 50 % of its cap: the trim (`XTRIM MINID`) is behind or the feed observer stopped.

### XtnlFeedPendingOld
The oldest un-acked feed entry is older than 30 s: the feed observer is stuck (its task circuit pages too).

### XtnlClockOffset
Clock offset above 50 ms: the node fails its hard check. `chronyc tracking`; never step the clock by hand.

### XtnlArmFailed

The ARM (optional, `XTNL_ARM_ENABLED=1`) has at least one FAILED scope (design §B14): it gives no advice for the
positions the scope covers; ingestion, Oversee and the gate are unaffected. The immediate ping names the scope, the
reason and the clear command. Run `python -m src.ops arm failed show`, fix the recorded cause (the ping and the
refusal of a clear name the request to run first, for example `md_rebuild` or `md_writer_reset`), then
`python -m src.ops arm failed clear <scope> --reason <text>`. The ARM never sends orders.

### XtnlRedisMdMemoryHigh

The optional market-data store `redis-md` (only with `XTNL_MD_ENABLED=1`) is above 70 % of its `maxmemory`
(`noeviction`). `md-writer` has paged "redis-md memory high" and sheds TICK data in its fixed order (design §A8);
BROKER series, their indicators and the rollback sets are never shed. Ingestion, Oversee and the gate are unaffected.
Follow `marketdata.md` "redis-md memory": check `md show`, the sizing (design §A5) and the unit's `MemoryMax`, then
raise `maxmemory` in `/etc/xtnl/redis-md.conf` (keep `MemoryMax` at twice it) or reduce the demanded symbols.

### Balance moves and transfers (operator cash-flow refresh)
When an alert or a page shows an unexplained balance move, ask the leader to fetch the account's cash flows
since the roll now (read-only; audited; the orchestrator rate-limits it to once a minute per account):
```
$OPS cash-flows refresh <account> --operator <you> --reason "<ticket>: unexplained balance move"
$OPS cash-flows refresh <account> --since-ms 1763020800000 --operator <you> --reason "<ticket>: transfer since <time>"
```

## Rollback

Nothing to roll back: alerts change nothing. A silence added for a maintenance window expires by itself;
remove an early one with `amtool silence expire <id>`; re-enable CloudWatch actions with
`aws cloudwatch enable-alarm-actions --alarm-names <name>`.
